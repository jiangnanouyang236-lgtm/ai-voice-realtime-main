# 复杂任务编排协议 v1

> 状态：实现完成至功能开关保护的运行链路；默认关闭，尚未生产启用
>
> 适用范围：LLM Router 判定为 `X=complex` 的单轮复合请求
>
> 目标：在保留简单请求低延迟路径的前提下，为 MCP、视觉、条件判断和 `[EXIT]` 任务提供可校验、可打断的顺序执行协议。

## 1. 不变量

1. Router 小模型只分类，不拆分任务。
2. 复杂任务由主 9B 模型在低温度下生成结构化计划。
3. 模型只表达意图、依赖和参数；程序负责校验、排序、执行、超时、失败和打断。
4. 图片由程序通过当前会话 `session_id` 获取，再作为本轮多模态内容加入 LLM 请求；不把取图暴露为 MCP 工具。
5. 图片、Base64、过程播报和原始工具结果不写入普通对话历史。
6. 物理动作只能由已注册的 MCP 工具执行；`robot_id` 必须由服务端会话注入。
7. 终止型任务成功后立即返回 `[EXIT]`；终止型任务之前必须已经完成所有可执行的普通步骤。
8. 收到打断后不再开始任何新步骤；已经提交到外部系统的动作不能假装撤回。
9. 终止型任务开始前，必须确认此前需要用户听到的 TTS 已完成客户端播放，不能只确认文本已经生成或音频已经下发。
10. 不修改现有 ASR、LLM、TTS gRPC 方法、消息字段和流式方向；不改变 LLM 文本增量进入 TTS 的行为。任何协议变更必须单独讨论和批准。

## 2. 请求路径

```text
用户当前输入 + 最近五个完整对话轮次
  -> Router 4B
     -> C/W/R/T/U：沿用简单路径
     -> X：复杂路径
          -> 播放一条短等待语（不写历史）
          -> Planner 9B 生成计划
          -> Validator 校验并规范化
          -> Python Gateway Workflow Coordinator 顺序执行
          -> 最终综合回答，或终止型工具成功后 [EXIT]
```

复合意图检测必须发生在“机器人关键词直调”之前，避免“先移动再查天气”被提前缩减成一次移动。

## 3. 模型职责

### 3.1 Router 4B

- 固定低温度，只输出白名单分类代码。
- 当前请求包含两个以上独立目标、条件动作、工具与视觉组合或步骤依赖时输出 `X`。
- 不输出工具名、参数和执行顺序。

### 3.2 Planner 9B

- 温度固定为 `0.0`，只输出 JSON。
- 输入包括：当前原始请求、最近五个完整对话轮次、允许能力清单、终止型能力清单和最大步骤数。
- 不接收图片；只判断计划中的哪一步需要最新视觉。
- 最多生成 8 个步骤。
- 不生成 `robot_id`、`session_id`、鉴权信息、内部 URL 或文件路径。

### 3.3 多模态 9B

- 只在执行到 `vision_analyze`，或 `respond` 步骤声明需要视觉时接收图片。
- 最终综合可以一次性接收原始问题、已完成步骤的结构化结果和最新图片，避免重复视觉推理。
- 看不清、图片缺失或内容不确定时必须明确说明，不得猜测。

## 4. 计划协议

Planner 的顶层输出：

```json
{
  "version": 1,
  "goal": "结合今天的天气判断用户当前穿着是否合适",
  "steps": []
}
```

`plan_id` 不由模型生成，由服务端在计划通过校验后创建并绑定当前 `session_id`、`trace_id` 和 `round_id`。

通用步骤字段：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `id` | 是 | 本计划唯一，格式 `step_N` |
| `type` | 是 | `tool`、`vision_analyze`、`respond` |
| `intent` | 是 | 简短说明该步骤要完成什么 |
| `depends_on` | 是 | 只能引用前置步骤，禁止循环依赖 |
| `failure_policy` | 是 | `abort`、`partial_response`、`skip` |
| `terminal` | 是 | 仅终止型工具可以为 `true` |

### 4.1 工具步骤

```json
{
  "id": "step_1",
  "type": "tool",
  "intent": "查询青岛今天的天气",
  "tool_name": "websearch.search",
  "arguments": {"query": "青岛今天天气"},
  "depends_on": [],
  "failure_policy": "partial_response",
  "terminal": false
}
```

- `tool_name` 必须出现在本轮服务端允许工具集合中。
- 参数必须通过对应工具 Schema 校验。
- 模型给出的 `robot_id`、`session_id` 和鉴权字段一律拒绝；必要字段由执行器注入。
- `terminal` 由服务端工具策略表重新计算，不信任模型值。

### 4.2 视觉分析步骤

用于“先看图，再根据视觉结果决定后续动作”的场景：

```json
{
  "id": "step_1",
  "type": "vision_analyze",
  "intent": "判断用户是否举手",
  "output_key": "hand_raised",
  "allowed_values": ["yes", "no", "uncertain"],
  "depends_on": [],
  "failure_policy": "abort",
  "terminal": false
}
```

执行器在该步骤开始时获取最新图片，并调用一次多模态 9B。视觉结论必须限制为声明的结构化值；`uncertain` 不得触发物理动作。

### 4.3 回答步骤

```json
{
  "id": "step_3",
  "type": "respond",
  "intent": "结合天气和当前穿着给出建议",
  "depends_on": ["step_1"],
  "vision": "latest_required",
  "failure_policy": "partial_response",
  "terminal": false
}
```

`vision` 只允许：

- `none`：不取图。
- `latest_optional`：图片不可用时使用已有文本结果继续。
- `latest_required`：图片不可用时不得生成视觉结论，只能说明画面不可用并回答可回答的部分。

简单视觉请求不经过 Planner，直接执行一个隐式的 `respond + latest_required`。

### 4.4 条件执行

工具步骤可以声明一个受限条件：

```json
{
  "when": {
    "source": "step_1.hand_raised",
    "operator": "equals",
    "value": "yes"
  }
}
```

v1 只允许对前置步骤结构化结果使用 `equals` 或 `not_equals`。禁止模型生成任意表达式或代码。

## 5. Validator 协议

计划必须在任何工具执行前整体通过校验：

1. JSON 和版本合法，步骤数为 1–8。
2. ID 唯一，依赖存在且无环。
3. 步骤类型、字段、视觉模式和失败策略均在白名单内。
4. 工具存在，参数符合 Schema，机器人身份字段未由模型提供。
5. 条件只引用已经声明的结构化输出。
6. `respond` 不得声称执行物理动作。
7. 服务端根据工具策略重新标注 `terminal`。
8. 非终止步骤稳定拓扑排序；终止型步骤统一移动到最后。
9. 一个计划最多允许一个终止型步骤。
10. 终止型步骤不能被其它步骤依赖，且后面不能存在任何步骤。
11. 复杂计划必须且只能包含一个最终 `respond`；它必须依赖所有需要向用户汇总的非终止步骤。
12. 存在终止型步骤时，`respond` 必须位于终止型步骤之前，随后由程序插入播放完成屏障。

首次计划无效时，允许 Planner 基于错误摘要低温重试一次。第二次仍无效时不执行任何工具，回复“这个任务有点复杂，我暂时没能安全地安排好，你可以分开告诉我。”

如果用户一次要求多个无法共存的终止型任务，例如“先跳舞再拨打视频”，本轮不执行其中任何一个，明确说明一次只能开始一个接管型任务。禁止静默丢弃。

## 6. Executor 协议

### 6.0 运行位置与边界

- Python Gateway 负责 Workflow Coordinator：工作流生命周期、打断、TTS、播放完成屏障和最终 round 状态。
- LLM 服务负责 Planner、视觉/文本推理，以及通过受控内部调用执行现有 MCP 能力。
- Go Gateway 和 Rust Client 不理解业务计划，只继续提供现有 interrupt、playback report 和过期轮次隔离。
- 当前 Rust Client 已会上报 `playback_complete` / `playback_interrupted`，Go M1 也会转成 `playback.report`；v1 不需要修改客户端消息协议。
- 不能直接把当前 LLM 服务内部自由工具循环扩展成工作流执行器，因为它无法独立确认客户端是否已经播放完上一段 TTS。
- 实现阶段如需 Python Gateway 与 LLM 服务交互，应新增独立、受功能开关保护的 Workflow 内部接口；不得修改或复用特殊文本标记污染现有 `LLMService.StreamChat`。
- 原有 `STTService.RecognizeSpeech` / `StreamRecognize`、`LLMService.StreamChat`、`TTSService.StreamTextToSpeech` 均保持兼容和原有流式方向。
- Workflow 最终综合文本仍必须按生成增量立即送入现有 TTS 双向流，禁止为了编排等待整句、整段或完整回答。

### 6.1 状态

```text
PLANNING -> VALIDATING -> RUNNING -> RESPONDING -> COMPLETED
                    \-> FAILED
任何非终态 -> CANCELLING -> CANCELLED
终止型工具成功 -> EXITED
```

工作流状态至少包含：

- `plan_id`、`session_id`、`trace_id`、`round_id`
- 当前 `step_id` 和每步状态
- 结构化步骤结果
- `cancel_requested`
- 是否已经提交副作用
- 是否已经发送 `[EXIT]`

### 6.2 顺序执行

- v1 所有步骤顺序执行；暂不并行调用多个工具。
- 每一步开始前、等待期间和结束后检查取消状态。
- 依赖未成功且无法生成部分结果时，跳过依赖步骤。
- 过程播报使用模板，不由 Planner 自由生成，也不写入普通历史。
- 最终只把用户原问题和最终助手回答写入普通对话历史。
- 机器人 MQTT 工具返回发布成功，即按当前业务定义将该步骤判定为成功并继续后续步骤；不等待设备物理完成 ACK。
- MQTT 明确发布失败时步骤失败；发布结果未知时仍不自动重试，避免重复下发。

### 6.3 图片获取

- 图片只通过当前 LLM 服务已有的内部 Go Gateway 接口按 `session_id` 获取。
- 必须校验 HTTP 状态、JPEG 格式、大小、会话归属和 Gateway TTL。
- 图片在执行到对应步骤时再获取，避免使用计划开始时的旧画面。
- 图片仅存在于本轮内存和模型请求中，不落盘、不写日志、不写对话历史。
- 日志只记录 `frame_id`、大小、年龄和状态。

### 6.4 终止型任务

- 巡逻、回桩、建图、跳舞、唱歌、视频呼叫等继续由服务端策略表判定为终止型。
- Validator 将唯一终止型任务移动到最后，不区分用户是否强调原始顺序。
- 执行前可以透明播报“该任务开始后我会进入待机，我先完成前面的内容”。
- 如果终止型任务之前生成了天气、查询或综合结论，Workflow Coordinator 必须等待对应 `playback.report` 中 `report_type=playback_complete`，并校验匹配的 `round_id`、`playback_id`，再开始终止型工具。
- Python Gateway 在发送该段 TTS 前创建以 `(session_id, round_id, playback_id)` 为键的等待项；收到匹配回执时完成等待。为避免回执先到的竞态，应保留有界、短 TTL 的最近回执缓存。
- `playback_interrupted` 直接取消等待和剩余工作流，旧轮次或不匹配的回执不得解除屏障。
- 等待播放期间收到 interrupt、播放失败、会话关闭或超时，不得继续执行终止型工具。
- 播放完成屏障是 Validator 自动插入的内部步骤，不由 Planner 生成。
- 复合计划中的终止型任务必须在屏障前的最终 `respond` 中预告，例如“今天有雨，建议带伞；现在为你拨打视频电话”。
- Gateway 在综合音频下发完成后先发送同轮次 `done(exit=false)`，只用于让 Rust 完成本轮播放并上报 `playback_complete`。
- 收到匹配回执后才执行终止型工具；工具明确成功后再发送同轮次的延迟 `done(exit=true)`，不生成第二段重复确认 TTS，状态为 `EXITED`。
- Rust 已支持在播放结束回到 `AwakeIdle` 后接受匹配轮次的延迟退出；Go M1 在收到最终结构化终态前持续转发该控制消息，因此 v1 不新增客户端消息类型。
- 单独的简单终止型请求继续沿用现有固定短句和 `[EXIT]`。
- 工具失败：不得发送 `[EXIT]`，状态为 `FAILED` 或生成失败说明。
- 工具结果未知：不得自动重试，避免重复副作用；说明当前结果无法确认。

## 7. 失败规则

| 情况 | v1 行为 |
| --- | --- |
| Planner 超时或输出无效 | 低温重试一次；仍失败则不执行工具 |
| 只读工具瞬态错误 | 在工具策略允许时重试一次 |
| 只读工具最终失败 | 根据策略生成部分回答或终止依赖步骤 |
| 副作用工具明确未提交 | 可以按工具策略重试一次 |
| 副作用工具已提交或结果未知 | 不重试，不声称成功 |
| MQTT 工具明确发布成功 | 按业务定义判定步骤成功，不等待设备完成 ACK |
| 图片缺失、过期或无效 | 不猜测；保留其它已成功结果并说明无法看到画面 |
| 视觉结果为 `uncertain` | 不触发依赖的物理动作 |
| 终止任务前的播放屏障失败或超时 | 不执行终止型工具，保留当前会话并说明失败 |
| 终止型工具失败 | 不发送 `[EXIT]` |
| 最终回答失败 | 使用已完成结果生成固定降级说明 |

## 8. 打断协议

1. Rust/Go 发来的现有 `interrupt` 继续取消当前播放和 Python Gateway 活跃轮次。
2. Python Gateway 同时向 LLM 工作流发送 `cancel_requested`，并取消当前可取消的 Planner、模型、MCP 等待任务。
3. Executor 在每个步骤边界再次检查取消状态，绝不开始下一步。
4. 打断发生后不再发送旧计划的新 TTS；迟到文本、音频和工具结果按 `round_id` 丢弃。
5. 已经发布的 MQTT 或已被外部系统接受的副作用不能回滚；只记录结果并停止后续步骤。
6. 打断后的新用户语音创建新的 `round_id` 和 `plan_id`，不得继续旧计划。
7. 重复打断必须幂等。
8. 等待播放完成屏障期间的打断优先于终止型任务，确保视频呼叫、巡逻等不会在用户已经打断后迟到启动。

## 9. 历史与上下文

- Router：最近五个完整用户/助手轮次 + 当前用户消息，重点参考当前消息。
- Planner：与 Router 相同的规范化文本上下文，不包含图片 Base64、过程播报和内部工具协议文本。
- 主回答模型：规范化对话历史 + 当前请求 + 本工作流必要结果。
- Workflow：独立保存计划和步骤结果，不能占用普通对话历史条数。
- v1 工作流状态可先保存在内存，但必须随 session 清理；服务重启不恢复未完成的副作用任务。

## 10. 典型计划

### 10.1 简单视觉

“看看我今天穿的什么？”不进入复杂 Planner：

```text
simple + vision -> 获取最新图 -> 多模态回答
```

### 10.2 天气与穿搭

“查一下今天的天气，看看我穿的衣服合适吗？”：

```text
step_1 tool：查询天气
step_2 respond：依赖 step_1，vision=latest_required
```

最终多模态请求一次性包含原问题、天气结果和最新图片。

### 10.3 视觉条件动作

“看看我有没有举手，如果举手了就往前走”：

```text
step_1 vision_analyze：hand_raised=yes|no|uncertain
step_2 tool：when hand_raised == yes，调用移动工具
step_3 respond：说明判断和执行结果
```

### 10.4 终止型任务重排

“拨打视频电话，然后查青岛天气”：

```text
规范化前：call_video -> weather
规范化后：weather -> call_video -> [EXIT]
```

## 11. 验收矩阵

实现不得只验证正常路径，至少覆盖：

1. 简单聊天、单天气、单机器人动作延迟路径不回归。
2. 简单视觉有图、无图、过期图、无效 JPEG、超大图片。
3. 天气 + 视觉正常、天气失败、图片失败、两者均失败。
4. 两个城市查询 + 视觉综合，顺序和结果引用正确。
5. 普通动作 + 查询 + 终止型任务，终止型任务最后且只产生一次 `[EXIT]`。
6. 多个终止型任务被安全拒绝，不静默丢失。
7. Planner 非 JSON、未知工具、越权 robot_id、循环依赖、超过 8 步。
8. 在 Planning、工具等待、视觉获取、视觉推理、TTS 播放期间分别打断。
9. 打断后无后续工具调用、无迟到 TTS、无旧轮次 `done` 干扰新轮次。
10. 副作用结果未知时不自动重试。
11. 多轮指代：“那适合今天吗”能够使用文本历史，但不复用旧图片。
12. 四个不同 Robot 并发时计划、图片和工具结果严格按 session 隔离。
13. 查询结果 TTS 尚未播放完时终止型工具不得启动；收到播放完成报告后只能启动一次。
14. 播放屏障等待期间打断、断连和超时，终止型工具均不得启动。
15. MQTT 发布成功后工作流继续，且同一步骤只允许发布一次。
16. 复合终止任务只播放一次“结果 + 即将执行”语音；工具成功后不得重复播放确认短句。

## 12. 发布与回滚

- 新复杂编排必须置于独立功能开关后，初始默认关闭。
- 简单请求继续沿用当前路径。
- 原有 ASR/LLM/TTS 协议和简单 Chat 流是回归基线；复杂编排只能通过新增旁路能力接入，不能改变其消息字段和流式语义。
- 灰度期间记录 Router 分类、Planner 耗时、步骤数、各步骤耗时、视觉状态、失败策略、打断点和终态。
- 回滚只关闭复杂编排入口，不修改 Go-Python M1、WebRTC、ASR、增量 TTS 和现有简单工具路径。

## 13. 当前实现状态

V1 的独立协议、Planner/Validator、Workflow Runtime、Gateway Coordinator、
`plan_id`/步骤状态、取消传播、视觉注入和终止任务播放屏障均已实现并有单元/集成测试。

生产默认仍为 `LLM_COMPLEX_WORKFLOW_ENABLED=false`。因此当前结论是
`IMPLEMENTED`，不是生产 `LIVE_VERIFIED`。V3 发布保持默认关闭；未来启用时必须在
目标 Runtime Snapshot 下单独验证复杂工具组合、打断、终止任务和副作用不重放，
不能用 Router 的 `X=complex` 分类命中代替工作流闭环证据。
